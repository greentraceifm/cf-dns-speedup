## 三、发现的问题

### P1：竞争槽交换会制造临时重复

2026-09-06 的竞争槽为：`auto3=104.17.130.125`、`auto4=104.17.158.61`。2026-09-07 新排序希望二者交换位置，脚本先执行 `auto3 -> 104.17.158.61`，而 `auto4` 已经是该地址，于是产生重复。

根因是 `choose_pending_primary_target` 已禁止单条主槽更新使用另一主槽当前持有的 IP，但竞争槽使用的 `choose_pending_target` 只选择第一个不匹配项，没有等价的去重保护。现有测试覆盖了主槽危险交换，没有覆盖竞争槽纯交换。

最小本地复现已确认当前函数会输出：

```text
auto3.test  104.17.158.61  104.17.130.125  3.87  4.32  challenger
```

若下一周期排序不变且 Cloudflare 可用，脚本通常会再把 `auto4` 改为 `104.17.130.125`，恢复两个不同 IP；但在此之前冗余已下降，且遇到 API 失败或候选变化时可能延长。

### P2：Cloudflare API 首次解析失败仍偶发

日志在 08-27、08-31、09-01、09-05、09-07 出现过 `Could not resolve host: api.cloudflare.com`，现有三次重试通常能恢复。09-07 最终更新成功，因此当前重试机制有效。

这属于外部解析/网络瞬时波动，不建议通过增加路由器 DNS、修改 PassWall 或降低门槛处理。应保留失败安全和自然周期重试。

### P3：维护审计工具曾有过期哈希

旧审计脚本保存了历史 `router-candidate-gate.sh` 哈希，会把已部署的新版本误报为 mismatch。本轮已使用当前部署哈希核验，四个脚本全部匹配。该问题只影响审计，不影响生产。

## 五、优化建议

### 优先级 1：修复竞争槽安全转换

建议只修改 `choose_pending_target` 及对应测试：

1. 若当前两个竞争槽的 IP 集合与目标集合相同，仅顺序不同，直接判定为无需更新；`auto3/auto4` 的名次顺序不应高于地址多样性。
2. 若目标集合确有变化，只允许选择“目标 IP 当前未被另一个竞争槽持有”的单条更新。
3. 若当前周期不存在安全的一条写入路径，则输出明确的 `awaiting_safe_competition_transition`，保留现有两个不同 IP，等待下一周期。
4. 增加纯交换、部分替换、单候选镜像和无候选镜像测试。
5. 保持每周期最多写一条 Cloudflare 记录，不批量交换，不临时使用未门控 IP。

### 优先级 2：增加更新前不变量检查

在 PATCH 前根据已读取的当前记录再次确认：当有两个不同的合格竞争候选时，本次单条更新不会让 `auto3/auto4` 相同。失败时安全退出并记录原因，不自动修复 DNS。

### 优先级 3：改善可观测性，不改网络拓扑

把 Cloudflare 重试次数、最终结果和安全退出原因写入结构化报告，便于区分瞬时 API 波动与真实链路失败。现阶段不需要新增 DNS 服务器，也不需要恢复旧 06:30 任务。

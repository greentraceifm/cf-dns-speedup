# CFIP 数据面脱离 OpenClaw 收口记录（2026-09-21）

## 结论

已确认夜间生产链路不依赖 `192.168.1.140`。

```text
数据面：.110 Sidecar -> 受限导出 -> VM36 .254 -> PassWall/Xray 门控 -> Cloudflare
维护面：本机 -> .140 OpenClaw -> .110 或 VM36
```

`.140` 是维护、审计和跳板，不是凌晨候选导出或 VM36 自动同步的生产中继。
因此 `.140` 夜间关机不会阻断 `.110` 与 VM36 的自然周期。

## 误报根因

一次手工核验把 OpenSSH 参数 `-F /dev/null`、`-T` 和额外的
`UserKnownHostsFile` 传给了 VM36 上的 Dropbear SSH 客户端。该客户端与
OpenSSH 参数语义不完全一致，导致命令返回 Dropbear 标识到标准错误、导出
正文为空。

这不是生产同步故障。生产脚本使用的调用方式是：

```sh
timeout 15 ssh -i "$SSH_KEY" -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  "$REMOTE_HOST" "$REMOTE_COMMAND"
```

今后在 VM36 上验证 `.110` 直连时，必须复用生产调用方式；不得自行加入
Dropbear 不兼容的 OpenSSH 选项。验证脚本必须分别检查退出码、标准错误为空、
导出字节数大于零、表头和候选行数。

## 最小优化结论

本次不需要重做架构，也不需要把 `.140` 改成常开机器。现状已经满足最短路径：

1. 保持 `.110` Sidecar 自然采集。
2. 保持 VM36 直接从 `.110` 拉取只读导出。
3. 保持 VM36 的真实 PassWall/Xray 门控和 Cloudflare 单记录更新保护。
4. `.140` 只在需要维护或审计时开机。

同步失败时，现有脚本会在拉取、格式或新鲜度检查失败后停止，不更新
Cloudflare；不能因为 `.140` 关机而恢复旧 cron、增加第二条同步任务或手工
改写 DNS。

## 回滚与边界

- 本次没有修改 VM36、`.110`、`.140`、Cloudflare、DNS、PassWall、cron、
  凭据或服务。
- 若未来 VM36 到 `.110` 的专用 SSH 直连真实失败，只停止自动同步并保留
  现有记录；先修复数据面认证或 `.110` 服务，不把 `.140` 临时加入生产中继。
- 网络级最终回滚仍为关闭 VM36 后启动 VM33，确保两台不同时占用
  `192.168.1.254`。

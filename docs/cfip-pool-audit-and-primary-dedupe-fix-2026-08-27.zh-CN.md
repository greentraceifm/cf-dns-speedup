# CFIP 候选池审计与主槽去重修复（2026-08-27）

## 结论

本次只读审计确认：候选池数量基本足够，但主槽当前仍存在重复，项目尚未达到“五槽尽量保持独立 IP”的完整预期。问题不是 DNS 污染，也不是 Sidecar 没有候选。

## 当前证据

- `.110` 最近自然 Sidecar 报告时间为 2026-08-26 20:10 CST。报告 5 行均为 HTTP 200，导出 3 个 observation 候选。
- Sidecar 导出候选的真实 Sidecar 代理路径速度约为 4.28–4.67 MB/s，均属于 `observation`，尚未达到优秀候选标志。
- VM36 主槽资格文件有 3 个候选，竞争槽资格文件有 3 个候选，竞争 watchlist 有 2 个候选。
- `champion-pool.tsv` 有 10 个条目：4 个 stable、5 个 watch、1 个 challenger；其中 4 个标记为 `promotion_ready`。因此池不是空的，但真正近期、同路径且可直接用于主槽的候选数量仍然有限。
- 当前主槽为 `auto=104.17.129.81`、`auto1=104.17.129.81`、`auto2=104.17.134.190`，`auto` 与 `auto1` 重复。五条记录在三路 DNS 和 Cloudflare 只读结果一致，说明解析链路一致但内容本身重复。
- VM36 PassWall、Xray、四个监听、Google/YouTube、项目锁和 `.110` 三个必要容器均通过只读检查。

## 根因

主槽重复修复原来只使用有限的排名候选。当前主槽中仍然健康且唯一的槽位可能因为排序位置靠后而被排除；同时，重复修复没有把全部已通过竞争资格的候选纳入修复池，导致可以安全去重时仍生成不完整的主槽计划。

## 已完成的代码修复

`sidecar-auto-sync.sh` 的重复主槽计划现在：

1. 将全部合格候选纳入重复修复池，而不是只取排名前 3 个。
2. 优先保留当前仍合格且唯一的主槽。
3. 只替换重复出现的后续槽位。
4. 保持 3.5 MB/s 竞争门槛、4.0 MB/s 主槽门槛、三日门控、25% 正常晋升门槛和每周期最多一条 Cloudflare 写入不变。
5. 不改变竞争槽在候选不足时镜像稳定主槽的原设计。

按当前生产数据重演，下一次主槽修复计划为保留 `auto=104.17.129.81` 和 `auto2=104.17.134.190`，将重复的 `auto1` 规划为已通过门控的其他候选；不会手工改写 DNS。

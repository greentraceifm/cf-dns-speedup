结论：**不需要停用 CFIP 或回滚 VM36，但当前不应继续扩大自动晋升逻辑，也不应手工批量改写五条记录。应先修复跨池去重和 VM36 本地 DNS 空答案的最小检查/修复路径。**

## 四、确认的新问题

### 问题 A：主槽与竞争槽跨池重复

当前只读结果：

| 记录 | 地址 |
|---|---|
| auto | 104.26.1.38 |
| auto1 | 104.17.153.15 |
| auto2 | 104.17.129.81 |
| auto3 | 104.26.1.38 |
| auto4 | 104.17.158.61 |

`auto` 与 `auto3` 重复。该问题发生在 9 月 14 日主槽晋升后，时间线与现象吻合。

### 可能根因

当前 `sidecar-auto-sync.sh` 的决策顺序是：

1. 先构建主槽目标；
2. 主槽晋升可以更新一条主槽记录；
3. 只有没有主槽待更新时，才处理竞争槽；
4. 每周期最多更新一条记录。

现有去重检查主要保护三个主槽内部，竞争槽逻辑主要保护两个竞争槽内部。主槽晋升将 `auto` 更新为原竞争候选 `104.26.1.38` 后，同一周期不会再更新 `auto3`；下一周期如果主槽已不重复，主槽内部检查也无法发现 `auto` 与 `auto3` 的跨池重复。

这属于**新发现的跨池不变量缺口**，不是此前已经修复的“竞争槽内部交换重复”问题。此前修复仍然有效，但覆盖范围不够完整。

### 建议的最小修复

在任何计划、排序和写入前，构建五条记录的全局地址集合：

- `auto`、`auto1`、`auto2`、`auto3`、`auto4` 必须全局唯一；
- 主槽晋升候选不得等于任何竞争槽当前地址；
- 竞争槽候选不得等于任何主槽当前地址；
- 如果一次只能更新一条记录，优先选择不会制造重复的目标；
- 如果主槽晋升会占用竞争槽地址，则本周期进入安全等待，或只更新竞争槽为已验证的不同候选；
- Cloudflare PATCH 前和 PATCH 后只读核验都必须检查五槽全局唯一。

修复应先本地 mock 测试，再在 VM36 建 root-only 备份并原子部署。不得先手工 PATCH `auto3`，因为这会绕过项目门控和回滚记录。

## 五、确认的新问题 B：VM36 本地 DNS 对 auto3 空答案

实时查询结果：

- `192.168.1.1`：`auto3 -> 104.26.1.38`
- `192.168.1.254`：空答案
- `1.1.1.1`：`auto3 -> 104.26.1.38`

其他四条记录在三路查询中均有一致结果。

Cloudflare 只读 GET 对五条记录均返回 HTTP 200，`auto3` 内容为 `104.26.1.38`。

### 判断

这更像 VM36 自身的 DNS 查询/缓存/转发路径问题，而不是权威 DNS 内容被污染。当前代理访问 Google/YouTube 仍正常，因此它暂未造成整体外网中断，但会影响 VM36 自己对 `auto3` 的健康判断和后续自动化决策。

### 建议的最小诊断顺序

1. 只读检查 VM36 的 `/etc/resolv.conf`、DNS 监听和 resolver 配置来源。
2. 对 `auto3` 连续查询 3 次，确认是稳定空答案还是一次性超时。
3. 比较 `nslookup auto3 192.168.1.1`、`nslookup auto3 192.168.1.254` 和 `nslookup auto3 1.1.1.1` 的返回码与 TTL。
4. 只清理 VM36 本地 resolver 缓存或重载其 DNS 客户端配置，前提是确认不会重启生产 PassWall 或修改路由器 DNS。
5. 如果仅 VM36 本地解析异常，自动同步应把该记录标记为 DNS 不确定并安全退出，不得据此改写 Cloudflare。

本次不建议增加 DNS 服务器数量。当前权威内容和 `.1`、公共 DNS 一致，增加上游只会扩大变量，不能解决跨池重复逻辑。

- 竞争槽内部顺序交换造成重复：已有专门修复，不等同于本次主槽与竞争槽跨池重复。

### 本次新问题

- 主槽晋升后与竞争槽共享同一个 IP，暴露了全局五槽去重不足。
- VM36 对 `auto3` 空答案，暴露了本地 resolver 视图与权威/其他观察点不一致。

## 七、优化优先级

### P1：修复五槽全局唯一不变量

这是最值得修复的代码问题。它会减少备用路径多样性，但暂时没有破坏主代理连通性。修复目标是“安全等待或安全单条转换”，不是强行补齐所有槽位。

### P2：补充 VM36 本地 DNS 空答案保护

在自动同步读取五条记录时，若任意一条在 VM36 本地 resolver 为空或与权威 GET 不一致，进入只读告警/等待状态，不执行 Cloudflare 写入。

### P3：把五槽全局唯一纳入回归测试

至少增加以下 mock 场景：

- 主槽晋升目标等于竞争槽当前 IP；
- 主槽更新后竞争槽需要同步换出；
- 单条写入无法同时完成交换时，必须安全等待；
- 五条记录任意重复时，只允许选择不制造新重复的目标；
- DNS 视图空答案或三路不一致时禁止写入。

### 暂不做

- 不恢复旧 06:30 cron；
- 不降低 `3.5 MB/s` 观察门槛；
- 不增加 DNS 上游；
- 不扩大扫描规模；
- 不改订阅、凭据、PassWall 版本或路由；
- 不手工 PATCH 五条 Cloudflare 记录；
- 不因为 `.110` 直连超时而改动生产网络。

## 八、最终建议

当前最短安全路径：

1. 保持 VM36、PassWall、Sidecar 和现有 DNS 服务继续运行。
2. 下一步先做五槽全局去重修复的本地 mock 测试和专家复核。
3. 同时做一次 VM36 本地 `auto3` resolver 的只读诊断；若确认只是缓存问题，再单独安排低风险缓存重载。
4. 修复部署后等待一个自然周期，不手动补跑同步。
5. 只有自然周期确认五槽全局唯一、三路 DNS 一致、Cloudflare 只读一致，才将本次问题关闭。

本次审计没有发现资源不足、PassWall 进程丢失、Sidecar 未运行、Cloudflare 权威记录损坏或候选池完全枯竭问题。核心问题集中在**跨池去重协议**和**VM36 本地 DNS 视图一致性**两个边界上。
